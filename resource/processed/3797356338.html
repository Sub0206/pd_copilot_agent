CoreSuite NAPC : Travelers - Check Vehicle/Member Counts

Created by Former user on Oct 25, 2019

Description

DescriptionIn Travelers CARS system, certain entities are only allowed to have a set number of occurrences. This method will be used upon issuance of an OOS transaction. The method looks ahead at future transactions, both issued and in-process. It will count the number of additions for the identified entities in the current transaction. The system will then go to each of the future transactions and do a similar count including any deletions happening in those transactions. The objective of this is to ensure that if the system were to carry forward to any subsequent transactions we will not exceed the set limitations of CARS.
 
Based on the outcome of the counts, return codes will be sent back to the transaction for configuration purposes. If the limitation is going to be exceeded an error message will be configured to the user explaining that the limit will be exceeded if this transaction is carried forward so the issuance of the transaction will be prohibited by configuration.
The information for the Entities with limitations is below:
 
30006 - Vehicle Max of 4 Vehicles 
30011 - Member Limitation varies based on question 30011_3 - Member Type
 
            Licensed Operator (L) - max of 6
            Excluded Operator(E) - max of 2
            Unlicensed (U) - max of 11 
 
This new method will perform the future-looking counts and determine if any of the included constraints are violated. The method provides return codes to indicate the findings of the different counts, and reason codes to indicate the status of the transactions that the counts was violated on. If one of the counts exceeds the limit, the method will stop after the first constraint is violated, and not check further constraints.
 
Counting Algorithm
  1. The method will first count the number of entity occurrences in the current transaction that are within the scope of interest for the validation. It will keep track of C_IDs and Occurrence Identifiers for each occurrence if any are configured. Pre-existing, added, and deleted occurrences will be included in the count.
     
  2. The method will then loop through all subsequent transactions and validate the corresponding occurrences within that transaction. For each occurrence of interest, it will
     
    a. Compare the C_ID of the occurrence in the subsequent transaction to the list of C_IDs that correspond to the entity type. If there is a match on the C_ID, then no change to the count is recorded since the occurrence already exists.
     
    b. If there is no matching C_ID, the method then checks the configured occurrence identifiers against the occurrence identifiers associated with the items already recorded in the count.
     
          i. If a matching occurrence identifier already exists in the list make no change to the count.
          ii. If no matching occurrence identifier already exists in the list then add 1 to the relevant counter and record the C_ID and occurrence 
              identifier, if configured, in the count.
     
    c. The method validates the accumulated counts against the constraint values provided. If any of the counts exceed the constraint value the method will set the Return Code based upon the constraint violated, and the Reason Code based upon the status of the transaction where the count was found to exceed the constraint. If the status is Closed, Reason Code is set to 1, if the transaction is Open, Reason Code is set to 2.
