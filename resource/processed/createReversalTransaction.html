CoreSuite NAPC : createReversalTransaction

Created by Former user on Oct 25, 2019
Description

This method creates one or more reversal transactions based upon the transactional context when the method is called. 

The reversal transaction will negate all changes in the issued transaction being reversed with the exception of any Q-Group 0 Question answers. 

In essence any answers or occurrences added will be marked as deleted.  Any answers or occurrences deleted in the original transaction will be marked as added in the reversal transaction.  Any updated Questions will have the current and previous values switched. 
Once the data manipulations are complete, the Action specified by the Step Attribute will be run on each reversal transaction created.

Supported Action TypeStandard
ConstraintsMust be executed from within a policy context. 
Suggested DependenciesNone
Notes

Typically used to support Out of Sequence processing where the transactions being replaced must be reversed in a downstream system before being reapplied.  Also used to support back out of a transaction as well.

Any premium fields that need to have their values reversed will need to be treated via XSL and upload to do the -1 (or whatever factor) multiplication and upload back to the transaction.

If the method returns a non-success return code, all changes should be rolled back.

The method will not perform any validation of the transaction being reversed.  The configuration should only provide for the use of the method in the appropriate contexts.

Identifying the Policy Transaction to Reverse

The rules for identifying the transaction to be reversed are dependent on the current transaction in context and the overall state of the policy at the time the method is invoked.  In most cases, any existing reversal transactions will be ignored.  The only exception to this is when the current transaction is a Reinstate as described below.

If the current transaction is an OOS replacement transaction, identified by a Removal Code of A or M, or having a corresponding transaction with a removal code of P, then create a single reversal of the corresponding original transaction with the same GT ID and Version and a Removal Code of P.  In this scenario, the new method is being called from within the Macros being run by the OOS method creating the replacements.

If the current transaction is an OOS Cancel, identify any active subsequent issued regular category transactions, excluding RENEW, transactions effective on the date of a RENEW, and CA/RE pairs, with a removal code of L with a reversing transaction ID and version equal to the current transaction’s transaction ID and version. If no transactions are found, look for any with a Transaction Effective Date later than the current Cancel transaction using the same exclusions as above. Process the identified transactions in Effective Date, issue date order descending.

If the current transaction is a Reinstate and the corresponding Cancel Transaction is associated with removed transactions (Removal Code is L and Reversing identifiers match the Cancel), verify that there are no other not-removed standard transactions created and issued since the Cancellation was created.  If no post-cancellation transactions are found then create reversals for any issued regular category transaction marked with a Removal Code of L associated with the Reinstate’s partner Cancel transaction that has a reversal established.  In this case the method will be cloning the original transaction itself rather than creating an actual reversal.  Process these in ascending Effective Date, issue date order.  Cancel/Reinstate pairs would not be included since they are not marked with the Cancel identifiers when they are removed.  Run the Macro on the Reversal as with any other reversal creation.

If none of the above conditions are met by the transaction in context, then create the reversal for the current transaction in context.  This is the processing required by a Back Out or other single transaction removal.

Configuration Requirements

The use of this method in an OOS change context must always be preceded by the use of the appropriate OOS method so that the impacted transactions are already replaced or marked for removal.  This method requires those marking in order to identify the transactions to be reversed.

Any Q Group 0 questions that need to have their values reversed will need to be treated via XSL in an upload to do the -1 (or whatever factor) multiplication and upload back to the transaction.  This should happen in the Action Macro run by the new reversal method on the reversal transaction.

If the method returns a non-success return code, all changes should be rolled back by the Outcome.

The method will not perform any validation of the transaction being reversed.  This is significant in the case of the current transaction reversal.  The configuration should only provide for the use of the method in the appropriate contexts.  In-process transactions, Flag/Event, and other disqualifying criteria should be handled by the configured use of the method via Dependencies.

Any installation that is using reversals must include the new method in the Action that will issue a Reinstate since it is not possible to detect an OOS Cancel’s Reinstate to conditionally execute the method in a Step.  The method must precede the issue Step in the Action.
