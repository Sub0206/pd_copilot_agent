Update Policy Transaction via Excel Spreadsheet



DescriptionUpdates the current in-context policy transaction based upon the information passed in as an Excel file using a specified template and interface (I-Tag) to process the provided occurrences.

The use of this method is predicated on the Action being called after a File Upload Overlay has been processed and placed a .xlsm file into the user's session where the method will look to obtain it. The file contents provide the upload input to the process, and the method accepts and supports all the same upload Step settings as those used by the Update Policy Transaction upload internal method.

An Excel template as an .xlsm file specified as an Attribute on the Step provides the layout and instructions for what information is being uploaded from the Excel spreadsheet.

The template may only have one detail row in it, but the row can have questions included from multiple Entities. The Entities included must be related in a direct hierarchical relationship across the row. All levels of the hierarchy above the lowest level entity of interest, starting with a direct child of the Policy entity, must be represented. Any format settings included on the cells in the detail row will be ignored by the upload.

Column headings, literals, and Policy Questions may be included in the file above the single detail row. Nothing may be included below the final detail row in the template.

Metadata, stored in cell comments for any cells that should be interpreted by the upload, will provide the mapping between the occurrences in the policy transaction and any special instructions for the mechanically-necessary columns that also must be included in the spreadsheet. These include a column designated to hold the occurrence IDs, one for an Update (ExtAction) Action upload instruction, and a deletion indicator to be used if the export results become input to an upload. The deletion indicator will not be used by the upload, but only exists to support the user making changes to the spreadsheet before uploading.

Metadata instructions for the cells of the detail row are comprised of either a Q-tag or mechanical column designation along with a visibility indicator and any additional special instruction for the column. The Policy level data cells use a similar format but do not require the use of the special values for ExtAction, ID or the delete checkbox since the Policy occurrence's ID is always known, is always assumed to be an Update, and is not allowed to be deleted. Policies may not be created using this mechanism. Only policy transaction updates are supported. The transaction must already exist and be in context for the upload to work.

The metadata for a cell should be the only text in the cell's comment and must be formatted like

Q-Tag or Control Tag|visibility|instruction
Where the pipes (|), visibility, and instruction are optional.

Examples:

Q_30006_5|Show|Literal
Q_30006_5|Hide|Code
ExtAction|Hide
ID|Hide
Q_30006_1

Valid Control Tag values include:

Control TagDescription
IDIndicates that the column contains the occurrence ID for the row. It is expected that this column will be defined as being hidden in the export spreadsheet.
ExtActionIndicates that the column contains the update instruction for the row/occurrence. It is expected that this column will be defined as being hidden in the export spreadsheet.

The values in this column will be managed automatically by the export spreadsheet.
DeleteIndicates that the column contains the deletion indicator. This column will be presented as a checkbox and will contribute to the management of the ExtAction column in the completed spreadsheet.


Valid visibility values include:

Visibility ValueNameDescription
ShowShowIndicates the column will be shown or visible in an export spreadsheet or that it will not be hidden in the upload spreadsheet. If no visibility value is provided Show will be assumed.
HideHideIndicates the column should be hidden in an export spreadsheet or that it will be hidden in an upload spreadsheet.


Valid instruction values include:


InstructionNameDescription
LiteralDrop-DownIndicates that the column contains a literal associated with a configured code/literal pair in a drop-down format. The values will be provided in the template itself and the configuration to enable the drop-down will be provided as part of the template.

This designation indicates to the upload process that the column should be skipped for processing in favor of a corresponding Code column associated with the same Question.
CodeCodeIndicates that the column contains a code value associated with a configured code/literal pair.

The upload will use this column for the input to the processing.

Please note that if an instruction value is provided there must also be a visibility value specified. Instruction cannot be included alone.

The ID column on each row will provide the occurrence ID for the row and the corresponding occurrence's B-Tag will be used to determine which View in the Interface will be processed against the data in the row. Only one occurrence is supported per row. This means that only the columns relevant for the associated entity type being processed should contain values to be uploaded on the underlying policy transaction. The hierarchy will be depicted in the position and ordering of the rows such that any child occurrences of an occurrence will immediately follow that occurrence in the spreadsheet and be grouped together by entity type. Sibling Entity Type occurrences of the same parent occurrence do not need to be grouped together. Each row will be processed against the correct View under the provided hierarchy.

The upload spreadsheet will be interpreted one row at a time. The first non-blank cell will determine how an Add row will be treated by the upload. The entity type associated with that cell will be the entity type used to determine which View in the Upload Interface is used to process the contents of that row. The hierarchy of the data being uploaded will be implied from the way the rows are presented in the spreadsheet. As with the export, any occurrences that are a child of another occurrence will be presented immediately following that occurrence's row in the spreadsheet.

Processing of the rows and occurrences will end when the first non-blank cell in the row contains the string END or when 10 sequentially blank rows have been processed.

Data updates are supported using a facility very similar to the standard Upload feature of PolicyWriter. All Upload update processing such as Remedies, View Item Errors, applicability processing, etc. are supported by this method as well.|

ConstraintsMust be executed from within a Policy Transaction context.

Must have properly formatted Excel information provided as input to the Step.

Must have a valid template file provided.
Suggested DependenciesPolicy Statue = Open

removal_code<> P (Pending Removal) or R (Removed)
NotesThe Excel data to be uploaded will be obtained from a specific session variable that is used by the File Upload Overlay to capture the input from a user.

Once the upload processing has completed, the file contents previously stored in session will be removed.

The process used by this method loads all data from the spreadsheet into upload objects and then calls the upload process. As a result, logging and processing will parse the entire Excel file first before beginning the upload process.
