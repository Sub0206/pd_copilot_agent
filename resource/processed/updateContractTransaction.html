Supported Action TypeStandard
ConstraintsMust be executed from within a Policy Transaction context.

Suggested DependenciesPolicy Status = Open

NotesNone

XML Usage

This method requires Update XML to provide update instructions. Step should be configured with XML-Use set to Accept XML for Update. An Interface must also be specified to be used to process the updates.

Attributes

None

Upload Processing

The Upload methods of Account Manager allow background updates to information contained in the application. The feature requires input expressed in Adaptik Update XML format to provide the information necessary for updating the target policy transaction.

Upload Entity Processing

Updates to Entity occurrences are made using update XML according to the following rules:

All participants in the ancestry of the lowest level Entity being treated in the XML update must be included in Views for the XML Update Interface. This may mean that lightweight Views need to be created for Policy and any other relevant parent nodes in the ancestry.

Items in the XML are matched to the Views using the XML tags provided. Aggregate or Entity-level tags will identify the Entity Type that the aggregate corresponds to, and Views will use the information in the XML aggregate to drive the processing of the updates. Questions are matched to their answers using the XML tags configured for each Question within the Entity Type.

View ordering within the Interface used to process the update is extremely important. Views are processed in sequence order, and the sequence should at least correspond to the ancestry order (parents followed by children) at a minimum. A View that contains items such as multi-value fields or secondary parents should be processed only after the corresponding Entity occurrences have been processed.

A specific View will be executed repeatedly if multiple nodes or entity-level tags appear in the update XML with the tag that corresponds to the View's Entity Type. The order in which these repeated items are processed is determined by the order in which they appear in the XML (e.g. all vehicles will be processed together in the order in which they appear in the XML). After a View and all of its associated XML nodes have been processed, the next View defined within the Interface will be processed against its corresponding XML nodes.

The policy entity must have the ExtAction and ID (always 1) included as attributes on the root level node in the XML. If the ID is not included on the Policy entity, 1 will be assumed. When updating an existing policy transaction, MC_ID, CT_ID, and VERSION_NO must be included to identify the transaction.

An ExtAction attribute will appear on each Entity occurrence in the XML and will determine the processing applied to the Entity occurrence. The following Table details the valid values for this attribute:

ValueDescription
AAdd Entity occurrence and populate from question answers supplied
DDelete Entity occurrence and all associated question answers
UUpdate the Entity occurrence using the question answers specified.


Note: The only ExtAction value allowed at the POLICY level is U - Update for this method. Policy transactions cannot be added or deleted using this mechanism. The value A is reserved for when a policy is being initially created.

Entities with an ExtAction of Delete or Update must have an included ID attribute that contains the occurrence ID, or the corresponding node in the XML must contain values for the Occurrence Identifier Questions configured on the entity to allow the corresponding occurrence to be updated.

The ID specified must be valid for the associated Entity type or an error message is logged, the user notified (if applicable), and the Entity is not processed. If the entity is the root entity, the entire XML message is not processed. If Occurrence Identifiers are used, the values specified must identify a valid occurrence within the hierarchy that corresponds to the current parent occurrence.

Entities are processed in the following way:

  • If the ExtAction is Delete, the identified entity occurrence and all of its related question answers and child occurrences are deleted. Additional questions are not expected, and any questions that appear below the node in the XML are ignored with the exception of the Occurrence Identifier Questions. Another exception may be updates that are configured to be applied to a deleted occurrence.
  • If the ExtAction is Add, no ID is expected. If one is provided, it is ignored. The provided question answers are used to initialize the corresponding View(s) that provide the processing necessary to create the new occurrences. A subset of normal View processing is used to manage the information in much the same way as if it had been entered from a user page.
  • If the ExtAction is Update, the ID or Occurrence Identifier values on the entity are used to retrieve the existing question answers for the entity occurrence, which are then used to initialize the corresponding View. Next, the question answer values from the XML are applied to the view to update any questions that were included for that entity occurrence, and the View is submitted. A subset of normal View processing is used to manage the information in much the same way as if it had been entered from a user page.

Any View Item Errors triggered by the View processing will cause the associated messages to be logged and whether the request is to be rejected is determined by the corresponding Reject For Upload property on the View Item Error itself.

Upload View Processing Rules

During Upload, the following View processing rules will be applied:

The View types supported for update via XML include Detail and Updateable List. Any other View Types that are included are not processed in the Upload.

When a conflict exists between an instruction in the XML and a rule in a View, the View Definition is enforced and will override any instruction in the XML.

View processing that updates question values, such as derivation, will override any updates specified by the XML.

Information that appears in the XML, but has no corresponding View configuration is ignored. (i.e. Aggregates with no corresponding entities or elements with no corresponding questions on any View in the interface.)

Any question that is included in the View, but for which no information appears in the XML will retain whatever value already exists for it unless the View itself drives a change to the question's answer value.

Empty tags specified in the XML are equivalent to a Delete of the question answer.

Protection properties are ignored in processing the XML updates. As a result, protected answers can be updated, and setting Protection in the View definition has no effect on Upload processing.

Entities included in the XML that have no corresponding View definition are logged as an error and not processed. Any updates related to that Entity are ignored.

View Item Required settings are ignored for update processing. If the configurator wishes to truly require an item so that no occurrence should be created without it, the Upload Remedy value of Reject should be used, or a View Item Error can be configured to check for the presence of a value.

Upload Remedies are used when the information is processed as part of the XML processing. Any changes made via Upload Remedy are logged to the System Message Log Messages structures similar to the way Rule Reapplication records any changes it makes.

If a change requires Rule Reapplication, then Rule Reapplication may use the Rule Reapplication Remedies as appropriate. It is important to note that the Upload and Rule Reapplication remedies could conflict in this case, and the last remedy applied is what is finally reflected in the DB.

Rule Reapplication, when triggered, should be applied once late in the process and apply to the top-most changed node of information for the sake of efficiency. Rule Reapplication may be disabled using the Perform Rule Reapplication property on the Step that invokes the Upload.

If while adding a new Entity occurrence an answer is found to be missing or mismatched for a question with an Upload Missing Remedy or Upload Mismatch Remedy value of Reject, the entire update request is rejected, and an error returned to the user in the appropriate wrapper-level error mechanism.

If a configured View Item error becomes applicable while Upload is processing a View and the error has its Remedy Group Reject for Upload property set to Yes, based upon Outcome configuration the update request can be rejected and an error can be returned to the user in the appropriate wrapper-level error mechanism.

Restrictions

The following restrictions are included in the Upload feature:

The execution of any Actions associated with the views being processed by Upload is controlled by the property on the Action Step called Execute External Calls. If the value of this property is Yes, then Actions are invoked during View processing. If the value of the property is No, then no Actions are called during the Upload.

Updates to questions with Answer Options are made using the Code value between the XML tags. The LITERAL attribute is ignored, and need not be included in the Update XML.

Upload Basic Question Answer Processing

Questions are processed for an upload when they are included in a View in the Upload Interface as a View Item. The settings on both the question and the View Item, including Exceptions and Variations, determine how information is captured or created for the question on the policy transaction.

Within an Upload Interface, Views are processed in the order specified in the Interface, and View Items are processed according to their Tab Order configured in the View. As a result, what happens on one question can influence the behavior on other questions later in the order sequence.

Similarly, within each View Item, the order in which different aspects of View Item and Question configuration are processed can also influence or change the answer captured in the policy. An instruction that occurs later in the order can override one that occurs earlier so understanding the order in which the configuration settings are processed during an upload is important.

Answer processing is based upon the configuration that applies at the time the View Item is processed (Exception, Variation, and View Item Version can all change the configuration to be used).

At a high level, the order in which the configuration is processed for an individual question is:

  1. Single configured Answer Option
  2. Computation
  3. Answer Action Processing
  4. Default Value settings
  5. Input Values applied
  6. Applicable Remedies applied

How each of these aspects is used or interpreted is described in the sections that follow.

Single Configured Answer Option

Single configured Answer Option Answer processing comes into play when there is only one valid configured Answer Option for the View Item being processed. In that case, Account Manager will automatically select the single Answer Option and set the question's Answer to that value. Because this processing is the first to be applied, an answer configured with only one valid Answer Option will never have the Missing Remedy applied since it will always be populated before it gets to the Remedy processing.

If there is more than one valid Answer Option configured for the question, no additional processing is applied and no value is pre-selected.

Computation

Computation refers to the execution of a specific Computation Routine configured on the question as shown in the Figure below.



Figure 1 - Computation Configuration Example

Computation can be applied in one of two ways, Default or Derived, as specified by the Apply Computation/External Value as property.

Default Computation will only be performed the first time the question is being processed such as when a new occurrence is being added or when a question on an existing occurrence that was previously not applicable has become applicable. Once the question has been processed, the Computation will not be applied again even if the user goes in and removes the answer value.

Derived Computation will be performed every time the question is processed, so the answer value will be refreshed or reinstated each time the View is executed. Derived Computation will always override any value provided in the update XML.

Answer Action Processing

Answer Actions are used whenever the values for a question come from, or are constrained by, an external source. A question's Answer Action is configured on the Question Properties page by specifying an Action code in the Answer Action property as illustrated in the Figure below.



Figure 2 - Answer Action Configuration Example

Answer Actions are used by questions to support two distinct capabilities. One is to allow the Action to supply the question's answer (External Answer Value) and the other is to provide the External Answer Options for the question.

Answer Actions can be applied or executed in one of two ways, Default or Derived, as specified by the Apply Computation/External Value as property. Answer Actions can also be suppressed for an upload by configuration on the upload Action Step.

Default Answer Actions will only call the Action the first time the question is being processed such as when a new occurrence is being added or when a question on an existing occurrence that was previously not applicable has become applicable. Once the question has been processed, the Answer Actions will not be applied again even if the user goes in and removes the answer value, or if inputs to the Action are changed.

Derived Answer Actions will call the Action every time any of the identified input fields for the Action are updated, so the information may be refreshed or reinstated each time the View is executed depending on the input values. Specific input Questions can be configured to prevent a re-trigger of an Answer Action using the Retrigger action upon value change (Detail Action Only)? setting on the corresponding XML View Item in the input Interface.

When an Answer Action is configured on a question, Account Manager will check to determine if the Action needs to be called by checking if the Actions have been suppressed for the upload and if not, then checking the Action's input Question Answers and the Continue Process Code question associated with the Action. If Actions are not suppressed, one or more input Answer has changed, and the Continue Process Code question has any value other than Y (Yes), the Action will be invoked and the information returned made available for question processing.

Questions configured with Answer Actions fall into one of two distinct categories, those with External Answer Values and those with External Answer Options. How each is processed is described in the following sections.

External Answer Value

External Answer Value questions have an Answer Action specified but do not have an Answer Option Type of External Specific List.

When processing an External Answer Value question the value for the question is obtained from the data returned in the Action results. If multiple options for the answer, possibly in combination with other question answers, are returned in an intermediate list, then the Continue Process Code is set to IL and the answer is not set from the service.

If the Continue Process Code is Y or IL any value provided in the XML should be applied if the question is not a Derived Answer Action.

Like Derived Computation, Derived External Answer Values may override the value supplied in the update XML, however if the Upload Action Step has Actions suppressed, the XML value will be used instead and may cause the application of Remedies later in the process.

External Answer Option

External Answer Option questions have an Answer Action specified and have an Answer Option Type of External Specific List.

When processing an External Answer Option question the list of valid values for the question is obtained from the data returned in the Action results and is used to validate the answer value provided when Remedies are being applied.

If Actions are suppressed, then whatever value is provided in the XML will be used without being validated. As a result, any value given would never trigger the Mismatch Remedy later in the process.

If the Continue Process Code is Y, any value provided in the XML should be applied if the question is not a Derived Answer Action.

Default Value

Default Value processing is used when a question is being answered for the first time - either when a new occurrence is being created or when a question on an existing occurrence that was previously not applicable has become applicable. The Default value by itself is not used at any other time. It can however be used by a Remedy, which will fall under the Remedy Processing described later in this document.

When the question is first initialized in the View, any Default value specified will be used to initialize the question's Answer before any other processing takes place and the Mismatch Remedies will immediately be applied to any non-blank value set by Default.

Input Values Applied

Upload accepts update XML which specifies the changes or additions to be applied to the transaction. A value provided in the update XML is applied to the question being processed as its answer value. An empty XML tag will create an empty or missing answer for the question. If the tag is not present in the update XML, it is treated the same as if the user had chosen not to answer or change the question on the page.

A few questions are not permitted to be updated through upload. As a result, they ignore any input provided in the update XML. These include:

  • Process Date (30000-35)
  • Transaction Stage (30000-39)
  • Status (30000-40)
  • Quote Number (30000-42)
  • Transaction Creation User Id (30000-44)
  • Session - In Test Mode Ind (30000-80)
  • Global Contract Transaction ID (30000-95)
  • Session - Contract Transaction ID (30000-96)
  • Session - Contract Transaction Detail Mode (30000-128)
  • AM Brand (30000-130)
  • AM Theme (30000-131)
  • AM Request URL (30000-132)
  • Coverage Package (30000-133)
  • Session - Logged in User ID (30000-134)
  • Session - OOS Completion Code (30000-135)
  • Original Reference Date (30000-139)
  • State Type (30000-140)
  • Transaction Create Date Time (30000-154)
  • Transaction Removal Code (30000-155)

In addition, any questions defined with a Computation Routine or which use an Answer Action that have their Apply Computation/External Value as property set to Derived will not accept input values from the XML either, unless Actions are suppressed in the upload, since by configuration the Derived answer should be the one that is used.

Input values in the XML may end up overwriting values that result from activities in earlier aspects of the process such as Default Values or External Answer Values.

Applicable Remedies Applied

Remedies are the last item to be applied to a question's answer and are configured for a question in Question Properties on the Determination Settings tab illustrated in the Figure below. There are four Remedy Groups, and the specific Group to be used is specified on the upload Action Step.



Figure 3 - Upload Remedy Group Configuration Example

Remedies are applied last in the process so that they can be used to correct any erroneous value supplied by an earlier part of the process such as Default Values or Default Computation.

At the point where any applicable Remedies are to be applied, the question is evaluated for one of the two mutually exclusive conditions listed below.

MissingThe question is not answered or the answer is blank, empty, or null and either being processed for the first time or is required in the View.
MismatchThe specified answer has been compared to the question's configured data type and Answer Options (configured or external) and has been found to be invalid.

If a question's answer is found to be missing, the Missing Remedy that corresponds to the Remedy Group in use for the upload will be applied.

If the question is found to be a mismatch, the Mismatch Remedy that corresponds to the Remedy Group in use for the upload will be applied.

For more detailed information on Remedy processing, please see the section entitled Upload Remedy Behavior.

Question Processing Example

The following is an example of how the parts of the process described in this section can interact with each other. The example describes a single configured question and the properties that it has that influence how the answer is created or derived. Within the example, the actions that will be taken differ based upon what is contained in the update XML passed to the upload Action Step.

Question with Default Computation and Default Value
When Being Added/Created

If the update XML contains no XML tag that corresponds to the question, meaning that no explicit instruction was provided in the XML, the Computed Value would always be stored as the question's value. The Default Value would be ignored since at the point in the process where Default Values are applied the question would already have an answer through Computation.

If the update XML contains an empty XML tag that corresponds to the question, meaning that the XML is giving an explicit instruction to remove the answer value for the question, the question's value would be set to missing and the Missing Remedy would be applied. The final value would be determined by the Remedy instruction. If the Remedy instruction is configured to use the Default Value, the Default Value is stored as the question's value. If some other instruction is configured to be used then the Default Value will not be the value stored for the question.

If the update XML contains an XML tag that corresponds to the question and contains a value, meaning that the XML is explicitly providing a value to be used for the question, the value in the XML will be used subject to Remedy processing since Input Value processing occurs later in the process than Computation, and the Computation is a Default Computation not a Derived one.

When Being Edited

If the update XML contains no XML tag that corresponds to the question, meaning that no explicit instruction was provided in the XML, the value stored as the question's answer would be dependent on any existing answer for the question in the database. If the existing answer value is not empty/missing then the existing value will be used subject to Mismatch Remedy processing. If the existing answer is missing then the required setting in the View will determine how the question is processed. If the question is required in the View then the Missing Remedy is applied and will determine the final value for the answer. If not required, then the answer is left missing.

If the update XML contains an empty XML tag that corresponds to the question, meaning that the XML is giving an explicit instruction to remove the answer value for the question, the question's value would be set to missing and the Missing Remedy would be applied if the question is required in the View. In that case, the final value is determined by the Remedy instruction. If the Remedy instruction is configured to use the Default Value, the Default Value is stored as the question's value. If some other instruction is configured to be used then the Default Value will not be the value stored for the question.

If the update XML contains an XML tag that corresponds to the question and contains a value, meaning that the XML is explicitly providing a value to be used for the question, the value in the XML will be used subject to Remedy processing since the Computation is not applied because it is configured as a Default Computation not a Derived one.

Upload Remedy Behavior

Product Designer allows configuration of various remedies to adjust incoming information for each question in case its answer is missing or does not match the allowable value list or range for the question. These remedies are specified through the Upload Missing Remedy and Upload Mismatch Remedy Remedy Group question properties within Product Designer.

As discussed previously, a Remedy may be applied when an answer is either Missing or determined to be a Mismatch. The table below indicates when a Remedy will be applied, as well as which Remedy is applied, based upon the state of the Question's Answer and the presence or absence of a value in the update XML. "Answer Exists" means that the Question was processed previously and an Answer was created for it. "No Answer" means that the Question is newly applicable and is being processed for the first time.


The sections that follow describe the Remedy processing that is applied for each configurable remedy option.

Missing Remedy

An answer is determined to be missing if it is required or newly applicable in the View being processed, but no answer is provided. When the answer is missing, the appropriate Missing Remedy will be applied.

Missing Remedy Options

The following sections describe the behavior for each of the Missing Remedy Options.

If the Missing Remedy is set to Missing, the answer to the question is also set to missing. Missing is a state in which the question is recorded as being unanswered in the database.

Default

If the Missing Remedy is set to Default, the answer for the corresponding question will be taken from the Default value specified on the View Item or Variation that currently applies for the question in the View, as shown in the Figures below.

Figure 5 - Default Missing Remedy in Variation Configuration Example

Figure 6 - Alternate Default Missing Remedy Configuration Example

Highest Possible Value

If the Missing Remedy is set to Highest Possible Value, the answer for the corresponding question will be set to the highest value from the Answer Options that currently apply for the question in the View. The highest value is determined by the sequence number values of the Specific List of Answer Options, or the highest To value established for ranges.

Lowest Possible Value

If the Missing Remedy is set to Lowest Possible Value, the answer for the corresponding question will be set to the lowest value from the Answer Options that currently apply for the question in the View. The Lowest value is determined by the sequence number values of the Specific List of Answer Options, or the lowest From value established for ranges.

Reject

The Upload Remedies include an additional value, Reject, that the equivalent Rule Reapplication options do not include. If the Upload Missing Remedy is set to Reject and the answer is missing the entire upload request will be rejected and returned without further processing.

Mismatch Remedy

An answer is determined to be a Mismatch if it is applicable in the View being processed, but the answer provided is not found to be valid per the Answer Options or data type that apply on the question when the View is processed. When the answer is identified as being a Mismatch, the appropriate Mismatch Remedy will be applied.

Split Limits

Input answers are checked to determine if they are split limit-type answers by looking in the input answer for a slash (/) character. If one is found in the answer, the answer is treated as a split limit.

Split limit mismatches are determined by extracting the components around or between the slashes and comparing them to the components of the Answer Options in sequence from left to right. This processing essentially filters out the answer options to those that comprise the "best match candidate" so that processing for Remedies that rely on relative logic may only consider a subset of the total answer options. This processing also manages numeric relationships so that 0100 and 100 will be found to be the same value.

Similarly, if a position has no value, as in the first position of /1000, then it is treated as a wildcard and will match any input value such as 0/1000 or 55/1000.

Example

For example, if the answer value that is input to upload is 0100000/550000 and the answer options for the field include:

SeqAnswer Option
1050000/100000
2075000/150000
30100000/200000
40100000/500000
50100000/300000
60175000/300000
70200000/500000

The answer would be identified as a split limit and the answer components 0100000 and 550000 would be extracted from the answer.
The first component, 0100000, would be compared to the first component of each of the answer options, and since neither the answer component nor the answer option contain any alphabetic characters, a numeric comparison would be applied. After the first component had been compared to the full set of answer options, the resulting set of options remain as candidate matches:

SeqAnswer Option
30100000/200000
40100000/500000
50100000/300000

The second component of the answer is then compared to the second component in the remaining answer options. In this example, 550000 is compared against 200000, 500000, and 300000 in that order. No exact match is found, so a remedy would be applied. In the case of Split Limits, it is important to note that the remedy would be applied to the filtered set of answer options, and that the set is parsed in sequence order. In this example, a Remedy of Next Lower would select the 100000/500000 Answer Option. If the answer value provided had been 0100000/450000, the Next Lower would have returned 100000/200000 because it was the last value processed before one was found to be greater than one of the components. Processing assumes that the values are sequenced in ascending order and if the answers are not sequenced in that way the results may not be what is intended by the configurator.

If the input value or any of the answer options contain alphabetic characters, only an exact match is possible. None of the relative Remedies (Next Lower, Next Higher, Closest) will produce any results.

The following sections describe the behavior for each of the Mismatch Remedy Options.

Missing

If the Mismatch Remedy is set to Missing, the answer to the question is also set to missing. Missing is a state in which the question is recorded as being unanswered in the database.

Default

If the Mismatch Remedy is set to Default, the answer for the corresponding question will be taken from the Default value specified on the View Item or Variation that currently applies for the question in the View as shown in the Figures that follow.



Figure 8 - Default Mismatch Remedy Configuration Example



Figure 9 - Default Mismatch Remedy Variation Configuration Example

Alternate Default

If the Mismatch Remedy is set to Alternate Default, the answer for the corresponding question will be taken from the Alternate Default value specified on the View Item or Variation that currently applies for the question in the View, as shown in the Figures that follow.



Figure 10 - Alternate Default Mismatch Remedy Configuration Example



Figure 11 - Alternate Default Mismatch Remedy Variation Config. Example

Highest Possible Value

If the Mismatch Remedy is set to Highest Possible Value, the answer for the corresponding question is set to the highest value from the Answer Options that currently apply for the question in the View. The highest value is determined by the sequence number values of the Specific List of Answer Options, or the highest To value established for ranges.

Lowest Possible Value

If the Mismatch Remedy is set to Lowest Possible Value, the answer for the corresponding question is set to the lowest value from the Answer Options that currently apply for the question in the View. The Lowest value is determined by the sequence number values of the Specific List of Answer Options, or the lowest From value for established for ranges.

Reject

The Upload Remedies permit on additional value, Reject, which the Rule Reapplication options do not include. If the Upload Mismatch Remedy is set to Reject, and the answer provided is a Mismatch the entire upload request will be rejected and returned without further processing.

Closest Value

If the Mismatch Remedy is set to Closest Value, the answer for the corresponding question will be set to the closest value from within the Answer Options that currently apply for the question in the View. The closest value is determined by comparing the value given to the Answer Options in the specific list in sequence number order until the value is found to be between two values from the list. At that point, whichever of the values is closest numerically will be used. If the answer supplied is directly between two Answer Options, being closer to neither, then the lower of the values will be returned.

If the answer value given is not a Split Limit and the answer options are non-numeric, then the highest value by sequence number is returned.

If the answer value given is a Split Limit and the answer options are non-numeric, then no value is returned.

Next Higher Value

If the Mismatch Remedy is set to Next Higher Value, the answer for the corresponding question is set to the first valid value from the Answer Options that currently apply for the question in the View that is higher than the value specified. The value is determined by comparing the value given to the Answer Options in the specific list in sequence number order until the value is found to be numerically lower than the option from the list. If the value specified turns out to be higher than the highest option, the highest option by sequence number is used.

If the answer value given is not a Split Limit and the answer options are non-numeric, then the highest value by sequence number is returned.

If the answer value given is a Split Limit and the answer options are non-numeric, then no value is returned.

Next Lower Value

If the Mismatch Remedy is set to Next Lower Value, the answer for the corresponding question will be set to the last valid value from the Answer Options that currently apply for the question in the View that is lower than the value specified. The value is determined by comparing the value given to the Answer Options in the specific list in sequence number order until the value is found to be higher than the option from the list. At that point, the previous option is used. If the value specified is lower than the lowest option, the lowest option will be used.

If the answer value given is not a Split Limit and the answer options are non-numeric, then the lowest value by sequence number is returned.

If the answer value given is a Split Limit and the answer options are non-numeric, then no value is returned.

Configuring an Upload

This section of the document explains how a Product Designer user would configure an Action that uses Upload.

Creating an Action that uses Upload

Upload is an internal method that is invoked from an Action Step (applies to Standard Actions only). In our example, the Standard Action that will include an Upload as part of its processing is RATE.

Please note: In order to use the Upload Internal Method, the action must be configured as a Standard Action within the Policy Configuration area of Product Designer as illustrated in the following Figure.



Figure 12 - Configuring an Action for Upload

Creating an Action Step that uses Upload

Within the Steps of an Action, a Step can be configured to perform an Upload. Please note that the Upload requires XML to be used to provide the instructions for any updates. In the example that follows, the source of the XML is the prior Step, which makes a call to a Rating Engine. Alternatively, the Upload Step can be configured as the first Step of an Action that is used to support a Web Service. In this instance, the Web Service will be providing the XML for the Upload.

Creating an Interface for Upload

An Upload requires an update XML as input. The data contained in the update XML is processed based on the order determined by the sequencing of the Views in the Interface provided on the Upload Step. In the example in the Figure above, UPDunderwriting is the Interface specified in the configured Upload Action Step.

Interface Views are processed according to the Interface View Seq Number assigned to each. An individual View will be executed repeatedly if multiple nodes or Entity-level tags appear in the update XML with the tag that corresponds to the View's Entity Type. The order in which these repeated items are processed is determined by the order in which they appear in the XML (e.g. all vehicles will be processed together in the order in which they appear in the XML). After a View and all of its associated XML nodes have been processed, the next View defined within the Interface will be processed against its corresponding XML nodes. Views should be added to the Interface in an order that supports the processing desired and which keeps in mind the inter-dependencies of the Views in the Interface.

Multiple Views based upon the same Entity Type can be included in an Interface if it becomes necessary to process some items for an Entity Type at a different point in the process than other items on the same Entity. The Views will use the same XML nodes to provide their input, but will only accept the changes that correspond to questions included in the View. Any XML tags that do not correspond to questions in one of the configured Views in the Interface will be ignored.

Interface View sequencing is EXTREMELY important when processing the upload to ensure that policy data integrity is maintained. For example, if the XML received is adding both a child and grandchild of Policy, the grandchild View(s) must be sequenced after the child View(s) to ensure that the grandchild processing can occur without errors.

Nodes in the XML that have no corresponding Views defined for that Entity in the Upload Interface are logged as information and not processed. They do not trigger any error processing.

Special Processing of a View for Upload

Policy Transaction Status and Stage have no effect on an Upload. Upload will update an issued transaction unless prevented by configuration such as an Outcome that checks for the transaction's Status value, or a Dependency on the Upload Action or Step itself.

Data Type is enforced in the Upload. If an answer in the XML is not of the correct data type for the Question, the Mismatch Remedy will be applied unless the Remedy is Closest, Next Higher, or Next Lower. In that case, the answer will not be used and the Missing Remedy will be applied if one is configured for the question.

Creating a Complementary Trusted Source Upload Step

Upload processing can be weighty depending on the amount of configured rules inherent in the Product and specifically the Views used by the Upload. In some cases, it may be known that the information that is being received has already had the equivalent product rules applied, and should just be accepted as-is. In this case, it may be desirable to use a complementary Trusted Source Upload to capture as much of the information quickly and to leave the Upload Processing to only those fields that truly need to have the product rules applied. The Trusted Source sections that follow describe the scenarios in which these two mechanisms can be interwoven to optimize the processing of larger updates from entities such as Rating Engines and other internal systems.

Best Practices:

The following Best Practices should be considered when configuring an Upload:

  • In the interest of efficiency, only the updated or necessary questions should be included in update XML being provided to an upload for processing.
  • Similarly, only those questions that can or should be changed within the Action context should be included in the Upload Interface configuration. Adding additional questions introduces risk in terms of data integrity as well as resource utilization.
