Update Policy Transaction from Trusted Source

Please see the corresponding section in User Guide for more detailed information.
DescriptionSupports an expedited update of information on the policy transaction that is known to come from a trusted source where the product rules will have already been applied and do not need to be applied again in Policy Writer.

Trusted Source Upload is only available for updates to existing transactions, and will not be permitted to create new policies or transactions.

TSUpload will use any View types in the Interface; however the View Items will be treated as if they exist in an XML-type View so none of the capabilities of the Views that do not exist on an XML-type View will be used in TSUpload.

Capabilities that will not be included in TSUpload include:
  • Invoking Rule Reapplication when a Rule Reapplication sensitive question is updated
  • Changing the Exception in use due to an Exception Factor question being updated
  • Updating Multi-Value questions when the Multi-Value target questions is updated
  • Updating Search information when a Search index changes
  • Updating Linked questions
  • Dependency Processing on View Items, Product Occurrences, etc.
  • Question Computation Routines
  • Answer Option processing/validation
  • Remedy Application
  • Applicability processing from the View (Will be driven by the answers in the XML on new occurrences)
  • Default/Required Coverage processing
  • Secondary parent creation. (updates will be supported for existing parent occurrences)
  • Derive or Default questions will NOT retrieve the target information (can be updated from the XML provided only).
  • Providing Answer Option Literals in subsequent XMLs
  • Those supporting Field Level Completeness
  • Maintaining Transaction History page information in parallel with Contract Answers
  • Capitalization and special character filtering of input answers
  • Validating the ID specified against the entity type associated with the XML tag.

Entity ProcessingUpdates to entity occurrences are made using the XML provided:

  • View ordering in the interface used to process the update is less important than in traditional upload processing because none of the order-based processing such as applicability and Dependencies will be performed as part of the update.
  • The policy entity must have the MC_ID, CT_ID, VERSION_NO, and ExtAction included as attributes on the root level node in the XML and must correspond to the MC, CT, and Version in context when the method is invoked.
  • An ExtAction attribute will appear on each entity occurrence in the XML and will determine the processing applied to the entity occurrence. Values include:


    ValueDescription
    AAdd entity occurrence and populate from question answers supplied
    DDelete entity occurrence and all associated question answers
    UUpdate the entity occurrence using the question answers specified.
    PAdd entity occurrence and populate from question answers supplied, but make it all appear and behave as if it previously existed. Typically used when PolicyWriter is not the authoritative source for the information.
    NUpdate the entity occurrence using the question answers specified, and make the changes appear and behave as if they were not a change. Typically used when PolicyWriter is not the authoritative source for the information.

    Note: The ExtAction value will not be validated for Trusted Source Upload. If an invalid value is provided, the entity will be ignored.

    Also: The only ExtAction value allowed at the POLICY level is U - Update. Policy transactions cannot be added or deleted using this mechanism.
  • Entities with an ExtAction of Delete or Update must include an ID attribute that contains the occurrence ID.
  • Entities included in the XML which have no corresponding View definition are not processed. Any updates therein are ignored, and no record is created indicating the disposition of the entity in the XML.
  • Entities are processed in the following way:
    • If the ExtAction is Delete, the identified entity occurrence and all of its related question answers and descendent occurrences are deleted. Additional questions are not expected, and any questions or occurrences that appear below the node in the XML are ignored.
    • If the ExtAction is Add, no ID is expected. If one is provided, it is ignored. The provided question answers are updated directly onto a new occurrence or the corresponding entity type. Applicability is driven by the answers provided in the XML and the questions in the View. If a tag is not present in the XML, then no answer is created on the occurrence. Likewise, if a tag is provided, but the corresponding question is not included in the View, no answer will be created on the occurrence. This means that items such as Continue Process Codes, and indicators that control other behavior on the occurrence should be included in the XML and the Views for any occurrences created using Trusted Source Upload.
    • If the ExtAction is Update, the ID on the entity is used to identify the entity occurrence to be updated. Then the question answer values from the XML are applied to the occurrence using the View to filter the answers in the XML. If the tag in the XML does not have a corresponding View Item in the View, the answer will not be applied to the occurrence. Also, if a View Item in the View has no corresponding tag in the XML, no change will be made, so any existing answer would be preserved or no new answer will be created.

View Driven Question ProcessingViews will be used only to filter the answers applied to the transaction as part of the update. View processing rules include:

  • All View types are supported for update via Trusted Source Upload. The View Items will be treated as if they exist in an XML-type View though so none of the functionality in the Views that is not supported on an XML-type View will be executed in TSUpload.* Information that appears in the XML, but is not defined in the View is ignored.
  • Any question that is included in the View, but for which no information appears in the XML will retain whatever value may already exist for it. No new answer will be created for it if none exists regardless of what the View configuration is.
  • Updates to Secondary Parent questions are supported so long as they reference existing occurrences and not occurrences being created in the same upload. The value passed in will not be validated, however, so no error is produced if the value does not refer to an existing occurrence of the correct entity type. Secondary Parent literals will not be created for these occurrences, however, so only the numeric identifier will be provided in any subsequent XML generated.
  • Empty tags are equivalent to setting the question answer to missing or empty if the contract answer already exists. If the corresponding question does not already have an existing contract answer, then no Contract Answer will be created and stored in the database (not even a missing one).
  • Protection properties are ignored. As a result, protected answers can be updated, and setting Protection in the View definition has no effect on XML update processing.
  • View Item required settings are ignored for update processing.
  • Upload Remedies are not used. The Trusted Source guarantees that any information provided will be correct so no remedies are applied, since no answer validation is attempted.
  • Rule Reapplication is not run, even if a Rule Reapplication-sensitive answer is changed.
  • Format, Min/Max Length, Data Type, and Required fields are not validated.
  • Answers are not subject to capitalization or special character filtering. Answers will be accepted exactly as transmitted.
  • Configured Computation is not performed.
  • Customization Routines will be supported, however the settings will only be taken from the base Question properties and not from any Variation or Exception, so if the Variation or Exception settings for the question require different treatment, the question should not be included in a TSUpload.
  • Default or Derived questions will not provide the value from the target question. Updates from the XML will be applied if provided.
  • Policy Impacts due to Multi-Value or Secondary Parent questions changing are not processed.
  • Search Indexes are not updated in the Search information cache.
  • Contract Transaction data including Version Number, Removal Code, Removal Code Timestamp, Transaction Type, Transaction Subtype, Transaction Description, Transaction Effective Date, Process Date, Reference Date, Term Number, Stage, Status, Status Reason, Transaction Source, Transaction Amount, Agent Code, Underwriting Date, Rating Date, Forms Date, Policy Effective Date, Policy Expiration Date, Freeze Stage, OOS Completion Code, Referral Status, User ID, Test Transaction Cycle Date, and Customer ID are not allowed to be updated via TS Upload.
Supported Action TypeStandard
Constraints
  • Policy transactions can only be updated using this feature. Additions or Deletions of policy transactions are not supported.
  • Secondary Parent occurrence references must be made only to occurrences that already exist in the database, and not to any occurrence being created in TSUpload.
Suggested DependenciesNone
Notes

Note: Using Trusted Source Upload requires special care. Validation is NOT included. There is a possibility that using it incorrectly will cause unexpected results.


XML Usage

This method requires Update XML to provide update instructions. Step should be configured with XML-Use set to Accept XML for Update. An Interface must also be specified to be used to process the updates.

Trusted Source Upload Processing

Account Manager requires a mechanism that will allow the upload of information from a Trusted Source in a way that maximizes application performance and throughput. Trusted Source refers to a system or service that has already been determined by the IT organization as an authorized source of Account Manager data where the information that is being received has already had the equivalent product rules applied. Services or applications labeled as 'Trusted Source' will not be subjected to the same level of data integrity checks usually associated with standard Upload processing.

By accepting input data from a Trusted Source, Account Manager is acknowledging the processing that has occurred in the remote system and as a result can allow for certain enforcement functionality to be turned off. Typically, an application is designated as a Trusted Source if it is another system within the organization whose validation logic is synchronized with Account Manager by the intrinsic type of processing that it does e.g. Rating engine, Underwriting Engine, Client File.

The Trusted Source functionality can be incorporated into customer processing via a configured Action Step that is typically one aspect of a larger running process configured in an Action. Trusted Source Upload itself is one of the internal methods that are available for configuration within an Action Step.

The following restrictions need to be considered when using the "Trusted Source" capability:

  • Trusted Source Upload is only available for existing policy transactions (contract transaction).
  • Trusted Source Upload does NOT allow for the creation of a new Policy or the creation of a new Policy transaction.
  • The Trusted source functionality is available for use in Standard Actions only.
Configuring a Trusted Source Upload

This section of the document will explain how a Product Designer user would set up a Trusted Source Upload. Throughout this document, the example that will be used is a Trusted Source Upload that updates a policy as a result of calling a rating engine.

Creating an Action that uses Trusted Source

Trusted Source Upload is an internal method that is invoked from within an Action Step of a Standard Action. In our example, the Standard Action that will include a Trusted Source upload as part of its processing is RATE.

Creating an Action Step that uses Trusted Source

Within the Steps of an Action, a Step can be configured to do a Trusted Source Upload.

Please note: the Trusted Source internal method requires XML to be used as the source of the updates. The XML will be applied against the list of Views appearing in the Interface specified on the Step. In our example, the source of the XML is the prior Step that makes a call to a Rating Engine. Alternatively, the Trusted Source Upload Step can be configured as the first Step of an Action that is called using the AM Gateway Web Service. In this instance, the Web Service request will include the XML to be used for the Trusted Source Upload.


In the example shown above, the Step, Update Rating Results, is configured to 'Accept XML for Update'. In our example, the XML is provided by the prior Step, which called a Rating Engine that returned XML containing changes to be applied to the transaction.

Please note the following required Action Step configuration settings:

Service Type must be specified as 'Internal Object'

Internal Method Name must be specified as 'Update Policy Transaction From Trusted Source'.

Similar to standard Upload processing, an Interface must be defined and specified for Trusted Source Upload processing. See Creating an Interface for Trusted Source Upload for details on interface creation.

An XSLT can be used to modify the structure of the XML before the Trusted Source Upload internal method is processed.

An XSLT can be used to modify the structure of the XML after the Trusted Source Upload internal method is processed. This may be useful when subsequent Steps re-use the same XML that was processed by the Trusted Source Upload.

Creating an Interface for Trusted Source Upload

Similar to standard Upload processing, a Trusted Source Upload requires an Adaptik Update XML input string. The data contained in the XML string is processed against configured Views in the order specified by an Interface. The name of the Interface is specified in the Product Action Step that is responsible for invoking the Trusted Source Upload internal method. In our example, UPDratingTS is the Interface specified in the Update PW using Trusted Source Action Step.

As with all other Account Manager Interfaces, the Trusted Source Interface will specify a set of Views that will be used to process the incoming XML. An Interface is an ordered set of configured Views. The order in which each View is processed is determined by the Sequence Number in the Interface. Similar to Standard Upload processing, a specific View will be run against all nodes within the XML that use the XML tag defined for the same entity type as the View in the order in which those nodes appear within the XML (e.g. all vehicles will be processed together in the order that they are listed in the XML). After a View and all of its associated XML nodes have been processed, the next View defined within the Interface will be processed against the appropriate XML nodes.

Please Note: The order of the Views included in an Interface is EXTREMELY important when processing the upload to ensure that policy data integrity is maintained. For example, if the XML received is adding both a child and grandchild of Policy, the grandchild View must be sequenced after the child Views to ensure that the grandchild processing can occur without errors.

XML nodes included in the XML that have no corresponding Views defined in the specified Trusted Source Upload Interface (whether they have corresponding Entity Types or not) are logged as an error and not processed. However, this condition does not reflect an error in the Trusted Source Upload processing.

Creating a View for a Trusted Source Upload

A Trusted Source Upload assumes that the provider of the XML will NOT provide invalid information for a Transaction Update. Because the Source is "Trusted", there are fewer product rules that are applied/checked. As a result, a Trusted Source Upload will process much faster than a standard Upload. Because of these restrictions, only views of type XML can be included in a Trusted Source Interface.

Trusted Source processing simply takes the answer provided in the XML and applies it to the database. As a result, any special behaviors or extended capabilities associated with the Question will not be updated by Trusted Source. Below is a list of Question categories/scenarios that are NOT supported in Trusted Source Upload.

If a Question / View Item falls into one of these categories, then the Question / View Item should NOT be included in the Trusted Source Upload Interface.

  • The question should not be one of the questions that also appear on the Contract Transaction table. These include: Version Number, Removal Code, Removal Code Timestamp, Transaction Type, Transaction Subtype, Transaction Description, Transaction Effective Date, Process Date, Reference Date, Term Number, Stage, Status, Status Reason, Transaction Source, Transaction Amount, Agent Code, Underwriting Date, Rating Date, Forms Date, Policy Effective Date, Policy Expiration Date, Freeze Stage, OOS Completion Code, Referral Status, User ID, Test Transaction Cycle Date, and Customer ID.
  • The question should not be Rule Reapplication sensitive unless the Trusted Source input also updates any impacted questions appropriately.
  • The question should not be the source of information for an exception factor.
  • The question should not be the target of a multi-value question
  • The question should not be used as a search index.
  • The question should not have an Answer Source of Linked.
  • Default or Derived questions will not provide the value from the target question. However if the remote entity provides a value for the question, it will be accepted and applied.
  • Secondary Parent questions are only allowed to be updated for parent occurrences that already exist in the database.
  • If the question happens to be a Secondary Parent question (which is allowed), the remote Trusted Source guarantees that the filtering dependency rules do not need to be checked.
  • Formatting rules will not be enforced for a specific View Item. The correct format should be given within the XML (examples include Time Stamps, Dates, Policy Numbers, SSNs, etc).
  • Applicability processing for both Questions and Occurrences will not be performed, so all answers provided in the XML will be applied without regard for whether a Question is applicable or not.
  • The question shouldn't be computed since computation routines are not performed. However if the remote entity provides a value for the question, it will be accepted and applied.
  • The Trusted Source guarantees the question's answer value so it does not need to be checked against answer options (lists and ranges). Therefore, Remedies for invalid answers will NOT be applied.
  • The question should not have a variation level other than Product Group.
  • Answer Option literals that are changed from the None exception will NOT be recognized.
Special Processing of a View for a Trusted Source Upload

Trusted Source Upload does process a View differently that a standard upload. The processing of the View Items and exceptions that differs from standard upload is noted below:

Information that appears in the XML, but is not defined in the View is ignored.

Any question that is included in the View, but for which no information appears in the XML will retain whatever value may already exist for it. No new answer will be created for it if none exists regardless of what the View configuration is.

Updates to Secondary Parent questions are supported so long as they reference existing occurrences and not occurrences being created in the same upload. The value passed in will not be validated, however, so no error is produced if the value does not refer to an existing occurrence of the correct entity type.

Empty tags in the XML are equivalent to setting the question answer to missing or empty if the contract answer already exists. If the corresponding question does not already have an existing contract answer, then a Contract Answer will not be created and stored in the database (not even a missing Contract Answer).

Protection properties cannot be specified for an XML View Item hence answers that are "protected" on standard views can be updated using this mechanism.

Upload Remedies are not used. The Trusted Source guarantees that any information provided will be correct so no remedies are applied, since no answer validation is attempted.

Rule Reapplication is not run, even if a Rule Reapplication-sensitive answer is changed.

Format, Min/Max Length, Data Type, and Required fields are not validated.

Configured Computation is not performed.

Customization Routines are supported (SEQNO, TS, LOCATION, etc).

Default or Derived questions dol not provide the value from the target question. Updates from the XML will be applied if provided.

Policy Impacts due to Multi-Value or Secondary Parent questions changing are not processed.

Search Indexes are not updated in the Search information cache.

As mentioned previously, Contract Transaction data updates are not allowed via Trusted Source Upload.

Alternate View processing will not occur within a Trusted Source upload. Only the view in the interface will be used to process the occurrences.

Default Coverages will NOT be added for a parent entity addition.

Sideways Impact Processing will NOT be executed during a Trusted Source Upload.

In the Views that support a Trusted Source Upload, the order of the View Items is NOT important since there is no dependency processing. Answers are simply applied to the database as they are processed.

Creating a Complementary Standard Upload Interface

Due to the limitations related to a Trusted Source Upload, an XML source may not be able to provide all of the information necessary to use a only Trusted Source interface. There may be specific tags for a Policy occurrence that may not "fit" into Trusted Source upload. When this happens, the following technique can be employed. The Product Designer user can identify the specific questions/tags that are not a candidate for a Trusted Source Upload. A complementary Detail View can then be created in which these non-candidate questions/tags can be placed. All of the power available in the standard Upload process is now at the disposal of the Product Designer user for those questions. A second Step that immediately follows the Trusted Source Upload Step can perform a standard upload that uses these complementary Views to further update the transaction. The benefits and speed of Trusted Source can be used where possible while the power of standard Upload can be used where required by the Question or scenario.

XML format for Trusted Source

Trusted Source Uploads require the format of Adaptik Update XML as specified in the standard Upload documentation, and must follow the following guidelines:

  • The policy entity must have the MC_ID, CT_ID, VERSION_NO, and ExtAction included as attributes on the root level node in the XML and must correspond to the MC, CT, and Version in context when the method is invoked.
  • The ExtAction values for each occurrence will not be validated for Trusted Source Upload. If an invalid value is provided, the occurrence will be ignored.
  • The only ExtAction value allowed at the POLICY level is U - Update. Policy transactions cannot be added or deleted using this mechanism
  • Entities with an ExtAction of Delete or Update must include an ID attribute that contains the occurrence ID.
  • The ID specified must be valid for the associated entity type or an error message is logged and the entity is not processed. If the entity is the root entity, the entire XML message is not processed.
XML Modification

As mentioned previously, there are instances where a Trusted Source Upload will not be able to process the entire XML that is passed into Account Manager. To allow a Product Designer user the flexibility to upload part of an XML string via Trusted Source Upload and the remainder of the XML via a Standard Upload, the XML that is received and processed by the Trusted Source Upload internal method will be modified and then left in memory so that the next Action Step can use the modified XML as an input.

If an entity has an ExtAction = "A" that is processed during a Trusted Source Upload, the ExtAction on the now-processed node will be changed to "U" and an attribute of ID="#" will be added where # is the appropriate occurrence id for the entity that was just added. This modification will allow any subsequent Step to appropriately update the newly added occurrence rather than attempt to add it again.

Likewise if the ExtAction = "P" on an entity that is processed during a Trusted Source Upload, the ExtAction on the now-processed node will be changed to "N" and an attribute of ID="#" will be added where # is the appropriate occurrence id for the entity that was just added.

ExtAction values of U, N, and S, and any on nodes in the XML that are not processed by the Trusted Source Upload will remain unchanged to be passed to a subsequent Step.

Best Practices:

The following Best Practices should be considered when configuring a Trusted Source Upload:

  • If a complementary standard Upload Interface must be created, then the Product Designer user should ensure that the questions are mutually exclusive between the two Interfaces.
  • When analyzing the questions in an existing View to see if they fit within a Trusted Source Upload, if 70% or more of the items View Items in the View do not "fit"" within the Trusted Source constraints, then it might be better to put the entire View into a standard Upload View Interface as there is overhead in processing the XML twice.
  • A Trusted Source View can contain many View Items but questions will NOT be updated unless there is a corresponding XML tag in the XML input. This processing is significantly different from standard upload where missing answers are created if the XML source does not provide an answer.
  • Because the Trusted Source View will NOT create missing answers, it is the responsibility of the Product Designer user to set up the data capture Views such that the questions are applicable through Dependency. Trusted Source can then update these questions. They will remain missing if the XML source does not contain any information.
